## 1. Шардирование

Приложение подключается к `mongos`, который маршрутизирует операции к двум шардам.
`configRS` хранит метаданные распределения данных. Между шардами распределяются
части шардированной коллекции.

На первом учебном этапе `shard1RS`, `shard2RS` и `configRS` состоят из одного
участника каждая. Это группы репликации без дополнительных копий на других узлах:
MongoDB требует replica set для шардов и config servers.
Состав кластера согласован с [документацией MongoDB](https://www.mongodb.com/docs/manual/core/sharded-cluster-components/).

План реализации:

1. Добавить `configSrv-1`, `mongos`, `shard1-1` и `shard2-1` в Compose.
2. Инициализировать `configRS`, `shard1RS` и `shard2RS`; подключить оба шарда через `mongos`.
3. Выбрать ключ шардирования по распределению данных и фильтрам запросов, создать
   необходимый индекс и включить шардирование коллекции `somedb.helloDoc`.
4. Переключить `MONGODB_URL` приложения на `mongodb://mongos:27017`.
   Направить скрипт загрузки данных через `mongos`.
5. Проверить наличие двух шардов и распределение документов между ними.

При реализации [задания 2](../mongo-sharding/README.md) выбран ключ `{name: "hashed"}`.
В API есть поиск по `name` и чтение
списка без фильтра. Последнее может обращаться к обоим шардам; само добавление
узлов не гарантирует ускорение каждого запроса.
Маршрутизация описана в [документации mongos](https://www.mongodb.com/docs/manual/core/sharded-cluster-query-router/).

## 2. Репликация

Каждый шард расширяется до **трёх узлов всего: одного primary и двух secondary**.
Для метаданных также запланированы три участника `configRS`.

| Группа | Участники | Данные |
| --- | --- | --- |
| `shard1RS` | `shard1-1`, `shard1-2`, `shard1-3` | Три копии данных первого шарда |
| `shard2RS` | `shard2-1`, `shard2-2`, `shard2-3` | Три копии данных второго шарда |
| `configRS` | `configSrv-1`, `configSrv-2`, `configSrv-3` | Три копии метаданных кластера |

Роли на схеме показывают один момент времени: любой подходящий secondary может
стать primary после выборов. При потере одного узла в группе остаётся большинство
из двух участников; при смене primary возможна краткая пауза записи.
Чтения приложения первоначально направляются на primary.
См. [репликацию MongoDB](https://www.mongodb.com/docs/manual/replication/).

План реализации: добавить secondary в каждую группу, указать все config servers
в конфигурации `mongos`, настроить отдельный том данных для каждого `mongod`.
Проверить состав групп, репликацию записей, выборы при остановке primary и
восстановление доступа приложения. Проверять отказы отдельно для каждого шарда
и для `configRS`.

## 3. Кеширование

Приложение управляет Redis по схеме **cache-aside**:

1. Перед кешируемым чтением проверить ключ в Redis (`GET`).
2. При попадании вернуть результат из кеша.
3. При промахе прочитать данные через `mongos` и сохранить результат в Redis с TTL (`SET`).
4. После успешной записи в MongoDB инвалидировать затронутый кеш (`DEL`).
5. При недоступности Redis выполнять чтение через `mongos`, ограничив время ожидания кеша.

MongoDB остаётся источником данных. Redis связан с приложением; прямое соединение
Redis с MongoDB для этой схемы не требуется.
Принцип описан в [документации Redis](https://redis.io/docs/latest/develop/use-cases/cache-aside/).

В [текущем приложении](../api_app/app.py) уже есть `RedisBackend`, настройка
`REDIS_URL` и декоратор `@cache(expire=60 * 1)` для `GET /{collection_name}/users`.
Поэтому начальный TTL в плане — **60 секунд**. Остальные маршруты сейчас
не помечены этим декоратором.

В [задании 4](../sharding-repl-cache/README.md) добавлены Redis и
`REDIS_URL=redis://redis:6379`; проверены попадания, промахи, истечение TTL,
инвалидация после POST и чтение из MongoDB при недоступности Redis.
Кеш допускает временно устаревшие данные; TTL ограничивает время жизни
записи, но не обеспечивает строгую согласованность при конкурентных чтениях и записях.

## 4. Service Discovery и балансировка

[Четвёртая схема](04-service-discovery.svg) показывает три экземпляра одного приложения:
`pymongo-api-1`, `pymongo-api-2`, `pymongo-api-3`. Перед ними — `api-gateway`
на Traefik, а `consul-1` (HashiCorp Consul, server + agent) хранит регистрации
и выполняет проверки доступности. Это выбранный вариант для учебного стенда.

### Пользовательский трафик

1. Клиент обращается к `api-gateway` по HTTP на внутренний порт `80`.
2. Gateway распределяет запросы между доступными API на порту `8080`
   по round robin с одинаковыми весами.
3. Каждый API использует общий Redis на `6379` и тот же `mongos` на `27017`.
   При попадании в кеш MongoDB не вызывается; при промахе или записи используется `mongos`.

Инстансы API не хранят локальные сессии или собственный кеш: общий Redis позволяет
любому из них обработать следующий запрос. POST на любом API удаляет общий ключ
списка соответствующей коллекции. Состав двух шардов и `configRS` сохранён из
третьей схемы: в каждой группе один primary и два secondary.

### Обнаружение инстансов и проверки доступности

Фиолетовые стрелки **API → Consul** обозначают регистрацию: у всех экземпляров
имя сервиса `pymongo-api`, но разные ID, адреса и порт `8080`. При запуске инстанс
вызывает `PUT /v1/agent/service/register` с HTTP-проверкой; при штатном завершении —
`PUT /v1/agent/service/deregister/<id>`. На одном учебном Docker-хосте регистрации
передаются агенту, встроенному в `consul-1`.
См. [HTTP API регистрации Consul](https://developer.hashicorp.com/consul/api-docs/agent/service).

Зелёные стрелки **Consul → каждый API** — периодические HTTP-запросы
`GET /health`. Планируется добавить этот endpoint с проверкой готовности API
работать через MongoDB; отказ необязательного Redis не делает API недоступным.
Начальные параметры для будущей реализации: интервал 5 секунд, тайм-аут 2 секунды.
При аварийном завершении не требуется вызов deregister: проверка становится
`critical`, и инстанс исключается из маршрутизации после обновления конфигурации.

Зелёная стрелка **Gateway → Consul** — чтение каталога и наблюдение за изменениями
по HTTP `:8500`. Gateway использует провайдер **Consul Catalog** с `watch: true`
и `strictChecks: [passing]`; адреса API берутся из каталога. Планируется также
`exposedByDefault: false` и тег `traefik.enable=true` на регистрациях приложения.
Это возможности [провайдера Traefik Consul Catalog](https://doc.traefik.io/traefik/reference/install-configuration/providers/hashicorp/consul-catalog/).

Новый инстанс включается после регистрации и успешной проверки. При удалении
регистрации или статусе `critical` адрес убирается из балансировки. Обновление
не мгновенно: оно зависит от проверок Consul и обработки изменений Gateway.
Для длительно недоступных инстансов можно настроить удаление регистрации через
`DeregisterCriticalServiceAfter`, предусмотрев повторную регистрацию восстановившегося API.
См. [проверки Consul](https://developer.hashicorp.com/consul/api-docs/agent/check).

## 5. CDN

[Пятая схема](05-cdn.svg) добавляет точки присутствия одного CDN в трёх условных
регионах: **Европа**, **Азия**, **Северная Америка**. В каждой группе показаны
пользователи и региональный кеш: `cdn-eu`, `cdn-asia`, `cdn-na`.
Точка присутствия (PoP, edge) — узел сети CDN, который доставляет файлы пользователям.
Это схема без привязки к конкретному провайдеру или списку его площадок.

### Источник статического контента

**`static-origin` — объектное хранилище оригинальных файлов магазина**:
CSS, JavaScript, фотографии товаров и шрифты. Подготовленные файлы загружаются
сюда при выпуске версии сайта или обновлении каталога. CDN обращается к этому
хранилищу по HTTPS на порту `443`.

На схеме каждый региональный узел связан со `static-origin` двусторонней стрелкой:
CDN запрашивает файл, хранилище возвращает его для доставки и заполнения кеша.
Такой режим называется **pull CDN**: файлы запрашиваются у источника по мере
необходимости. Работа кеша и origin описана, например, в
[документации CloudFront](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html).

### Маршрут запросов

1. Браузер запрашивает публичный файл через условный домен
   `static.mobile-world.example` по HTTPS. Сеть CDN выбирает подходящую точку
   присутствия с учётом сетевой доступности и задержки; на схеме показан региональный маршрут.
2. При **HIT** файл возвращается пользователю из кеша этого узла.
3. При **MISS** или необходимости обновить просроченную запись CDN обращается
   к `static-origin`, получает актуальный файл либо подтверждение его актуальности,
   обновляет кеш и отвечает пользователю.
4. Динамические запросы к `api.mobile-world.example` идут напрямую в Gateway.
   Далее сохраняется маршрут из четвёртой схемы: Gateway → API → Redis / MongoDB.

Домены с окончанием `.example` служат обозначениями на схеме. На пятом варианте
для внешнего API-входа запланирован **HTTPS `:443` с завершением TLS в Traefik**;
внутренние обращения Gateway к API остаются HTTP `:8080`.
CDN обслуживает публичную статику; ответы API и персональные данные в его кеш не попадают.

### Обновление файлов

Планируется использовать имена с хешем содержимого, например `app.8f3c.js`,
и длительный TTL для таких неизменяемых версий. При выпуске новой версии сайт
ссылается на новое имя файла. Для файлов с постоянным URL задаётся ограниченный
TTL; при срочном обновлении выполняется очистка (purge / invalidation) в CDN.
Удаление файла только из origin не очищает уже сохранённые региональные копии.
См. [версионирование файлов и обновление кеша](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/UpdatingExistingObjects.html).

### Результат задания 6

Подготовлена пятая схема, на которой показаны три группы пользователей,
три региональные точки CDN и общий источник статического контента.
Весь бэкенд из четвёртого варианта сохранён: три API, Gateway, Consul, Redis,
`mongos` и девять `mongod` в трёх группах репликации.

## Инстансы и сетевые связи

| Тип | Этап 1 | Этап 2 | Этап 3 | Этап 4 | Этап 5 | Порт |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `pymongo-api` | 1 | 1 | 1 | 3 | 3 | `8080`; с этапа 4 за Gateway |
| `mongos` | 1 | 1 | 1 | 1 | 1 | `27017` |
| `mongod --configsvr` | 1 | 3 | 3 | 3 | 3 | `27019` |
| `mongod --shardsvr` | 2 | 6 | 6 | 6 | 6 | `27018` |
| `redis` | 0 | 0 | 1 | 1 | 1 | `6379` |
| `api-gateway` / Traefik | 0 | 0 | 0 | 1 | 1 | `80` на этапе 4, HTTPS `443` на этапе 5 |
| `consul-1` / Consul | 0 | 0 | 0 | 1 | 1 | `8500`, HTTP API |
| CDN — региональные точки присутствия | 0 | 0 | 0 | 0 | 3 | HTTPS `443` |
| `static-origin` / Object Storage | 0 | 0 | 0 | 0 | 1 | HTTPS `443` |
| **Всего сервисных компонентов на схеме** | **5** | **11** | **12** | **16** | **20** | |

Пользователи и контейнеры группировки не входят в число сервисных компонентов.
Три точки присутствия принадлежат одному CDN. CDN и Object Storage — логические
облачные компоненты на схеме; число 20 не означает число Docker-контейнеров.

На схемах цветные контейнеры выделяют replica set; каждый цилиндр — отдельный
инстанс. Стрелками показаны обращения приложения к `mongos` и Redis, маршрутизация
к primary, работа с метаданными, мониторинг secondary и связи внутри групп.
`sync` обозначает обмен для репликации и heartbeat, `HB` — heartbeat между secondary.
Ответы возвращаются по тем же соединениям. Обнаружение primary входит в основную
связь с ним; после выборов `mongos` использует нового primary.

Для читаемости служебные обращения шардов к `configRS` и перенос чанков между
шардами не развёрнуты отдельными линиями. Их нужно разрешить во внутренней сети,
как и обмен между всеми участниками каждой группы. Шарды читают метаданные
из config servers, что описано в [документации config servers](https://www.mongodb.com/docs/manual/core/sharded-cluster-config-servers/).
